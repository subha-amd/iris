01 · recap

The fused region works — the win is real, and it told me where to look next

  • Prefill: 1.56× over the unfused MORI-dispatch → aiter-fmoe → MORI-combine baseline (1247 µs vs 1941 µs), correctness-gated.
  • We fuse the expert region: the gather produces the GEMM's layout, so 7 kernels collapse to 3 — no sort, no standalone quant, no scatter-combine.
  • Decode is a weight wall — the GEMM streams all 32 local experts' ~1.4 GB fp8 weights every step; fusion caps at ~1.25× there. That's why fp4 + the comm work matter more than more GEMM tuning.
The thread I'm pulling on

Our biggest single communication win didn't come from a better algorithm. It came from changing the order in which thread blocks issue their remote writes.

That's a scheduling decision — and right now it's hand-rolled. Making it a library concern is the contribution.

03 / 11
03 · the problem with hand-rolling it

That round-robin is right by luck, and it doesn't generalize

workload-blind

Balances count, not bytes

Round-robin assumes every destination carries equal bytes. Under the expert load imbalance Simran flagged — some experts get 8× the tokens — a hot expert's tile is far bigger, and cycling ranks equally leaves links unbalanced.

not reusable

Re-derived per collective

The gather has its own hand-rolled ordering. A future reduce-scatter will need a third. Every collective re-invents link balancing from scratch, with its own bugs.

a cliff, not a slope

The default is pathological

The order you get "for free" from a CSR grouped by destination is the 934 µs one. Miss the hand-tuning and you're 2.4× slow — silently. The good schedule is opt-in.

The schedule should be computed by the library from the declared demand and the measured link topology — not authored by hand, per kernel, once per collective.

2 · schedule

When & over which link

3 · execute

How it runs

lowers to IRIS primitives inside a HipKittens kernel — bulk-synchronous now, tile-fused later

four intents cover the MoE region + the TP collectives
tile_gather(tiles, src_map)              # dispatch: pull from owners
tile_scatter(tiles, dst_map)             # push to destinations
tile_reduce_scatter(tiles, dst, op=sum) # combine, all-reduce/2
tile_all_reduce(tiles, op=sum)          # rs + all-gather
the point

The author writes the declaration once. The bulk and fused executions are two lowerings of the same intent, and the schedule is shared across both.

The permutation space Osama called "insane and unexplored" — how many tiles to produce before you reduce — becomes a schedule the library searches, not a constant a human tunes.

  • IRIS gives device primitives (load/store/get/put/atomic) + one whole-tensor all_reduce. Tile collectives don't exist — so we hand-roll them.
  • HipKittens gives a gorgeous tile compute abstraction (register/shared tiles, MFMA) and no communication concept at all.
the gap, in one line

HipKittens describes tiles of compute. IRIS moves bytes between ranks. Nothing describes tiles of communication that a scheduler can balance and a GEMM can overlap. TileComm is that missing verb.

06 · the intuition, live

Order decides how many links stay busy at once

Each tick is one remote write, colored by its destination link (0–7). The moving box is the concurrency window — the blocks in flight together. The bar under each row is the window's busiest-link load: taller = more contention.

sorted → one link saturates spread → all 8 links share the load destination link 0…7 = hue

Sorted keeps ~1 link busy per window (the rest idle); round-robin and proportional keep all 8 busy. Same total bytes — 2.4× less wall-clock. This is the whole mechanism.

07 · the cost model & results

A calibrated scheduler — and an honest read of where it wins

A wave-based link-contention model (tilecomm/tilesched.py), calibrated so uniform combine reproduces the measured 934 / 386 µs. Three schedulers: sorted (naive), round-robin (today), proportional (byte-weighted, demand-aware).

scheduling vs the naive order a kernel author writes by default — the big lever, now impossible to miss

= lower bound

09 · the second direction · MXFP4 DeepSeek-R1

Memory is a non-issue — the blocker is a legitimate baseline

"will R1 even fit on 8 GPUs?" — checked
  • MI350X = 309 GB HBM each → 2.47 TB across 8.
  • R1 MXFP4 (403 GB) = 16% of HBM; fp8 (~671 GB) = 27%. Fits with enormous headroom.
  • The old wall was disk, not HBM — the node has 666 GB free on /data2, the model's already cached, and a live SGLang-MXFP4 container is on it.
status of the fp4 kernel work
  • Route-1 W4A16 decode is done & shipped — MXFP4 weights, hardware cvt_scalef32_pk_bf16_fp4 unpack: 1.6× GEMM, 1.11× region over fp8. Weight-only fp4 is the right decode choice (decode is weight-bound).
  • The honest gap: our fp4 comparison replayed a buggy, untuned captured aiter kernel. Beating it means nothing.
the plan — measure against the real production stack, in the realistic config

Run AMD's reproducible SGLang DeepSeek-R1-FP4 benchmark (already on this node), profile the MoE region under TP4 × DP2 + DP-attention + EP — not TP8, which inflates the all-reduce and isn't how R1 is served on AMD — and iterate the fused region against that trace. Simran offered to run the e2e; that's the gold denominator. Rule: never iterate against a kernel we captured ourselves.
