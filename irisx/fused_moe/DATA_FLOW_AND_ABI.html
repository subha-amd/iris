1 · The region at a glance — what fuses, and why no sort kernel

The production unfused region is 7 kernels: MORI EpDispatch → moe_sorting ×2 → dynamic_quant → fmoe_g1u1_silu → moe_sum → MORI EpCombine. We collapse it to 5 kernels. The whole expert region runs on the consumer rank against an expert-major packed buffer; tokens cross XGMI exactly twice — once in (gather), once out (combine).

Why there is no moe_sorting in the fused path (Awad's question). The unfused GEMM consumes a flat [token, H] activation buffer and needs sorted_ids / sorted_expert_ids to group tokens by expert. Our gather already groups: gather_pack writes each expert's rows contiguously into the packed buffer using the host route_segments map, so "sorting" is the placement. The GEMM then indexes experts by expert_row_begin (a 256-aligned prefix), and combine_pull inverts the placement with a host CSR. No sort/scan kernel, no scatter-to-sorted, no moe_sum.

2 · The 8-XCD execution model (read this before the per-kernel maps)

An MI355X is 8 XCDs × 32 CUs = 256 CUs. Every kernel here launches a 1-D grid of independent blocks (one block per expert-tile, per packed-row, or per destination-cell). The gfx950 hardware workgroup scheduler sprays blocks round-robin across the 8 XCDs (block i → XCD i mod 8), then round-robins across the 32 CUs inside each XCD. So consecutive blockIdx.x values land on different XCDs — there is no per-XCD affinity in the code; load-balance is a property of the round-robin + the task count.

The three load-balancing levers (all in the host task lists, none in the kernels)

  • Constant tile, variable count. Every expert uses the same tile height (BM=256 prefill, 16 decode). Expert imbalance is absorbed by the number of tiles: ⌈M_e / BM⌉. A hot expert simply emits more blocks. Each block is one entry in tasks[num_tasks,4] = (expert, m_tile, n_tile, expert_row_begin).
  • Spray over XCDs. Because the grid is flat and the scheduler is round-robin, a hot expert's many tiles land on different XCDs — no single XCD becomes the bottleneck for one expert. The padding tail (≤BM−M_e rows) is masked / MFMA'd to zero, never read by the next kernel.
  • Round-robin XGMI. The combine CSR is ordered so consecutive cells target different destination ranks, spreading remote-store bytes across all 8 XGMI links (sorted-by-rank was measured ~2.4× slower per byte).

4 · Input ABI — every buffer the region consumes & produces

"Where" = IRIS symmetric heap (allocated in identical order on every rank → identical offsets, so ctx.load/store(ptr, rank) resolves a peer's copy) vs. local HBM (never crosses XGMI). Shapes for DeepSeek-R1: H=7168, INTER=2048, N_FC1=4096, E=32 local experts, top-k=8, QGROUP=128 (NG=56).

Two ABI traps a vLLM integrator must know (from PRODUCTION_ABI.md):
  • Scale layout. We pack scales token-major [Mpacked, 56]. Production fmoe reads group-major [56, M_pad] — a transpose. Any code that hands our packed scales to stock fmoe (or vice-versa) must transpose or it reads numerically-wrong scales with no crash.
  • fc1 N-split. We assume the fused 4096 is [gate(0:2048) ‖ up(2048:4096)] (blocked, not interleaved). If the production w13 preshuffle interleaves per-128-block, silu_quant's gate/up split must match. (Flagged [NEEDS-NODE] in the ABI.)

4c · The two XGMI primitives (this is all of "IRIS" the region uses)

callused bysemantics
ctx.load(ptr, src_rank)① gatherread 128 bits from the same symmetric offset on a peer GPU over XGMI (a local deref when src_rank == cur_rank).
ctx.store(ptr, v, dst_rank)⑤ combinewrite bf16/bf16₂/uint4 to a peer GPU's accumulator. Cross-rank visibility is established by the host iris.barrier() (hipDeviceSynchronize + MPI_Barrier = system fence) that brackets each phase, so in-kernel ops are relaxed — no per-element fences.

The combine also has a rejected ctx.fetch_add scatter variant (kernel.cpp:1464): correct but XGMI-write-bandwidth-bound at fp32 (788 µs). The shipped pull does the accumulate locally in fp32 and stores bf16 → 386 µs, beating MORI EpCombine's 398 µs.
