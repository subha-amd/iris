DeepSeek-R1 MoE — the EP gather/scatter path (C4) and how we'll prove a fused win

One-line thesis (sharpened by measurement). In C4 the old TP all_reduce is replaced by a MoE all-to-all (EpDispatch → … → EpCombine). A device-side fused gather→pack→quant feeding a HipKittens expert GEMM is the right kernel — but the on-device data shows its decode value is to hide the gather under the unavoidable expert-weight stream (ceiling ~1.1–1.4×), not to beat a 1.76× that only exists at prefill-size batches. MEASURED on MI350: the decode MoE is a WEIGHT memory wall, not a gather wall

Per-kernel @ decode (M_e=4): moe_gemm fc1 145µs + fc2 85µs = 230µs GEMM · quant 9.9 · sort 5.0. T_local barely moves 515→238µs as M_e drops 64→4 — it hits a floor.
Why the floor. The expert GEMM streams all 32 local experts' ~1.4 GB of fp8 weights from HBM every decode step (940 MB fc1 + 469 MB fc2 → ~176µs at 8 TB/s, measured 230µs). Token count barely matters. Decode MoE is weight-bandwidth-bound. The cost model (moe_cost_model.py) now reproduces this: GEMM 86% of region at M_e=4, fusion ceiling ~1.1–1.4×.
The actionable insight (revised by data). The gather/dispatch+combine is real but only ~18% of the decode region. A fused gather→pack→quant wins by HIDING the gather+sort+quant+launch overhead under the unavoidable weight stream (expert-granular pipeline) — ceiling ~1.1–1.4× at decode, not 1.76×. Bigger decode levers: shard weights across more EP ranks, fp4 weights, or larger batch (turns the GEMM compute-bound).

Why the current 714µs vs 1255µs is not yet a fair baseline

Both numbers are real and useful, but they measure different regions at the wrong operating point.
SideWhat it includesWhat it MISSESµsM_e
production aiter.fused_moesort + quant + fmoe + moe_sumEpDispatch, EpCombine (the XGMI)1255~256
b1_dispatch (b0)XGMI gather + grouped GEMMquant, sort, and the combine entirely714~256
Three gaps to fix. (1) Region mismatch — production has sort+quant but no XGMI dispatch/combine; ours has XGMI gather but no quant/sort and no combine. They overlap only partially. (2) Operating point — both run at M_e≈256 (prefill-like). Real decode is M_e≈4, a 64× smaller point where BM=256 padding alone wastes the GEMM 64×. (3) GEMM dtype — production fmoe is native fp8; grouped_b0 is bf16-dequant (~2× slower MMA). The pipeline win comes from eliminating sort+quant, not a faster matmul.

How people actually benchmark fused-vs-unfused multi-GPU kernels (the recipe Tier 2/3 follow): define the region by I/O not kernel-count · capture realistic inputs (the trace M_e) · baseline = stock ops in sequence, device-event timed, warmup+median, clocks locked · multi-GPU region time = MAX over ranks · correctness gate (RMS) before timing · report at decode AND prefill · cross-check the harness's per-kernel times against the trace.

Next steps

Profiling still worth doing before the kernel design freezes

  • rocprof-compute (omniperf) on EpDispatch/EpCombine — VGPR / LDS / occupancy / achieved BW. Tells you if the gather is BW-bound (fusable) or latency/occupancy-bound (needs a redesign). Highest-value input for the kernel.
  • Per-layer/per-step M_e capture (abi/ROUTE_CAPTURE_SCHEMA.md) — the real decode distribution to feed the harness. Without it you benchmark the wrong operating point.
  • C2 control (EP off) — confirm EpDispatch/EpCombine disappear → proves the gather came from the EP flag, not just dp>1.
  • All-rank trace (not rank0) — needed for the MAX-over-ranks production denominator in Tier 3.

Kernel line

  • Match M_e to decode and re-run the Level-2 head-to-head over the full region (add the combine to b1_dispatch first).
  • Pin the cost-model constants; use it to set the target (close the gap to the perfect-overlap floor).
  • Then optimize the gather itself: current ep8_gather ≈210µs (at 8192 rows) vs production EpDispatch ≈30µs (decode) — measure ours at the SAME decode M_e to see the true gap.
